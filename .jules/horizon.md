## 2026-08-20 — Audit Log Cryptographic Migration
**Risk identified:** The legacy audit trail hash uses a weak 32-bit bitwise operation and naive string concatenation with delimiters (`|`), which is vulnerable to delimiter injection attacks and collisions. Over time, as this evidence chain grows and becomes critical for compliance, migrating away from this structurally insecure format will become nearly impossible without breaking validation of historical logs.
**Migration target:** Modern, secure hashing using standard structured serialization (`JSON.stringify`) to prevent delimiter spoofing, combined with a stronger synchronous hash (FNV-1a 32-bit) to preserve architectural synchrony, with a `hashVersion` schema evolution strategy.
**Migrated this session:** Introduced `generateAuditHashV2` using FNV-1a and `JSON.stringify`. Added `hashVersion: 2` to the `AuditTrail` schema. Fully integrated the V2 hash generator into `createAuditLog` as there are currently no downstream validators relying on the old format, avoiding async contagion. The legacy `generateAuditHash` function remains strictly for backward compatibility of legacy logs.
**Remaining:** Implementation of audit log validation and reading functions that can handle both V1 and V2 hashes.
**Next session:** Build the `validateAuditChain` function that seamlessly routes validation to the legacy or V2 function based on the `hashVersion` property of the log entry.
